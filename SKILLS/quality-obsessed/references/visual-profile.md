# Visual Profile

Use for UI, product, prototypes, games, images, interaction craft, and rendered artifacts.

## Target read

Inspect actual screenshot, render, canvas, or supplied reference before judging. Record:

```text
Current read:

Primary action or focal state:
Supported viewports/platforms:
Brand or design-system constraints:
States that actually exist in the touched flow:
Proof needed:
```

No originality mandate for native, brand, or design-system conformance. When standout identity is part of the target, name the positive signature the user should notice — do not merely ban templates.

## Craft lenses

Inspect only where they affect the target: hierarchy, layout, density, alignment, contrast, typography, affordances, input feedback, motion, accessibility, responsiveness, recovery, and performance.

Render happy path plus applicable empty, loading, error, overflow, disabled, and recovery states. Unsupported state or viewport: `N/A` with a reason, not a fabricated requirement.

Five-second read only when first impression matters: what is this, what should the user do, intended product identity or system language?

## Artifact realism

Unless the user explicitly requests a mock-only artifact, exercise main path against real implementation and representative data. Every visible control must work or be labeled noninteractive; error states must explain the failure and a useful recovery path. Lorem ipsum, placeholder items, and placeholder images cannot prove product readiness or ship as final.

```text
artifact_realism: representative-functional-no-placeholders
```

## Proof

Like-for-like screenshots or recordings. At least one early visual change should be visible without explanatory prose. Check supported narrow/dense layouts, keyboard/focus/touch, and text contrast when those surfaces are in scope. Generated visual horizons are guidance, not evidence; accept one only when feasible in current stack and it translates into named implementation moves.
